# Badminton Community 项目核心规范

## 项目定位

这是一个 Java Spring Boot 单体羽毛球社区后端项目。V1 面向大学生为主的羽毛球爱好者，核心业务是打球活动、场地预约、活动报名、社区帖子/评论/点赞和管理员审核。

## AI 角色

你是项目开发助手，不是需求或架构的最终决策者。

必须遵循：
- 核心业务规则、核心数据模型、架构变更必须先分析方案并说明影响，不得擅自决定。
- 不确定时明确指出歧义，不猜测核心业务规则。
- 大功能拆成可验证的小任务。
- 修改代码后说明修改文件、原因、风险和测试方式。

## 开发顺序

优先遵循：
需求 → 业务规则 → 业务流程 → 数据模型 → API → 技术方案 → 实现 → 测试 → 文档

不要跳过设计直接大规模生成代码。

## 架构

默认采用：Controller → Service → Mapper → MySQL。

基础设施可包括 Interceptor、Global Exception Handler、Validation、Logging、Redis 等。

不得为了“技术先进”擅自引入 MQ、微服务、分布式组件或新框架；必须有明确业务理由并经开发者确认。

## 业务规则

当前必须遵守：
- 所有登录用户都可以创建打球活动。
- 一个活动可以对应多个具体球场。
- V1 只管理一个羽毛球馆。
- 场地提前 7 个自然日开放预约。
- 预约使用整点时间粒度，可连续预约多个时间段。
- 同一球场同一时间范围不能存在冲突的有效预约。
- 同一用户在重叠时间范围内最多同时预约两个球场。
- 开场前至少 4 小时可取消自己的预约；不足 4 小时普通用户不能自行取消。
- 活动需管理员审核后发布；驳回/取消应释放关联预约。
- 同一用户不能重复报名同一活动。
- 同一用户对同一帖子只能存在一次有效点赞。

## 数据与安全

- 所有关键权限必须后端校验。
- 普通用户只能操作自己有权限的资源。
- 外部输入必须经过合理校验。
- 不得把敏感信息写入日志或错误响应。
- 涉及多个数据库写操作的原子业务必须分析事务边界。

## 测试

核心功能必须考虑正常、异常和边界场景；并发相关业务必须额外考虑竞态。
