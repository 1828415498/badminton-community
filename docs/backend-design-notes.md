# 后端设计、实现与面试速查手册

> 用途：记录本项目中已经确认的设计决策、后端实现规范及其面试表达。
>
> 原则：每一条都要回答“解决什么问题、为什么这样做、边界是什么”。没有经过代码、测试或文档验证的结论，不写成项目事实。

---

## 1. 设计时先问的四个问题

开始设计一个功能前，按顺序回答：

1. **业务事实是什么？** 例如：用户是否参加一个活动、某块场地某时段是否被占用。
2. **数据由谁拥有？** 例如活动信息属于 `activity`，场地占用属于 `reservation`，报名关系属于 `registration`。
3. **什么数据必须始终成立？** 即不变量，例如一条场地占用必须属于个人预约或活动占场之一。
4. **并发发生时，谁是最终防线？** 单行唯一性优先由数据库兜底；跨行统计、时间区间、跨表状态变化由 Service + 事务控制。

不要因为页面上有一个功能，就直接新建一张表或往某张表加字段。先确定它是一个实体、一个关系，还是从已有数据可计算出的结果。

## 2. 本项目的核心数据模型

### 2.1 六张核心表的职责

| 表 | 保存的业务事实 | 不保存什么 |
|---|---|---|
| `user` | 账号、密码哈希、昵称、角色 | 用户预约、用户报名 |
| `venue` | 场馆名称和地址 | 球场状态、预约数据 |
| `court` | 某场馆下的球场及其可预约状态 | 活动信息、报名信息 |
| `activity` | 球局信息、创建者、时间、人数上限、生命周期状态 | 具体球场、报名人数 |
| `reservation` | 某球场在某时间段被占用的事实 | 报名人数、活动成员 |
| `registration` | 某用户参加某活动的关系及状态 | 场地、活动时间 |

### 2.2 多对多关系的落地

关系型数据库不把“多个 ID”存成数组；多对多关系用关联表的一行一行记录表达。

```text
用户 ──< registration >── 活动
活动 ──< reservation  >── 球场
```

`reservation` 不只是普通中间表，它还带有开始时间、结束时间、状态、取消时间等属性，因此它是场地占用账本。

一个活动同时占用两块场地，会有两行预约记录：

| court_id | user_id | activity_id |
|---:|---:|---:|
| 1 | NULL | 42 |
| 2 | NULL | 42 |

### 2.3 预约账本不变量

`reservation` 的每一行必须恰好有一个归属：

```text
个人预约：user_id 有值，activity_id 为 NULL
活动占场：user_id 为 NULL，activity_id 有值
```

以下两种记录都是非法的：

```text
user_id=7,    activity_id=42  # 身份混乱，会误算为个人预约
user_id=NULL, activity_id=NULL # 没有归属者
```

对应 SQL CHECK：

```sql
(user_id IS NULL) <> (activity_id IS NULL)
```

这叫**不变量**：无论创建、取消、审核、报名等操作如何执行，该规则都必须始终成立。

## 3. 数据库与 Service 的职责边界

### 3.1 数据库适合兜底的规则

数据库适合表达单字段或单行层面的确定性规则：

| 规则 | 本项目实现 |
|---|---|
| 用户名不重复 | `UNIQUE(user.username)` |
| 同馆球场名不重复 | `UNIQUE(venue_id, name)` |
| 一人一活动只有一条报名记录 | `UNIQUE(registration.user_id, registration.activity_id)` |
| 一人一帖只能点赞一次 | `PRIMARY KEY(post_like.post_id, post_like.user_id)` |
| 外键引用对象必须存在 | FOREIGN KEY |
| 结束时间晚于开始时间 | CHECK |
| 预约记录归属恰好一个 | CHECK |

### 3.2 Service 必须负责的规则

Service 擅长需要上下文、跨行统计、时间判断、权限或多表原子性的规则：

| 规则 | 原因 |
|---|---|
| 同场同一时间段不能冲突 | 需要区间相交查询，且涉及多行并发 |
| 同一用户重叠预约最多两场 | 需要统计多条有效个人预约 |
| 同场连续占用不能超过两小时 | 需合并重叠或首尾相接的时间段 |
| 只可预约未来 7 个自然日 | 依赖服务器当前时间 |
| 距开场不足 4 小时不能自行取消 | 依赖当前时间和用户角色 |
| 活动驳回/取消后释放场地并取消报名 | 需在同一事务更新多张表 |
| 报名人数不能超过上限 | 并发下需要锁定、统计、写入的整体正确性 |
| 只有管理员可审核活动 | 依赖当前登录用户的角色 |

### 3.3 一个实用判断法

```text
能否用单条唯一约束或 CHECK 精确表达？
  是 → 数据库约束必须加，作为最终兜底。
  否 → Service 必须实现校验；若存在并发，还需要事务和锁。
```

不要只在前端做校验。前端校验只改善体验，任何人都可以绕过页面直接调用接口。

## 4. 索引设计

### 4.1 索引的职责

普通索引的主要职责是**加快定位数据**，不是自动保证业务正确。

```text
索引：更快找到候选记录
业务 SQL：判断记录是否满足业务条件
事务和锁：保证并发时检查与写入之间不被抢占
```

唯一索引例外：它除了加速查询，还能在数据库层拒绝重复值。

### 4.2 现有核心索引与查询路径

| 索引 | 支撑的业务查询 | 说明 |
|---|---|---|
| `reservation(court_id, start_time, end_time)` | 某块场地在某时段是否冲突 | 先按球场缩小范围，再按时间筛选 |
| `reservation(user_id, start_time)` | 我的预约、用户重叠预约统计 | 先定位用户，再处理该用户的时间记录 |
| `reservation(activity_id)` | 驳回/取消活动时批量释放占场 | 按活动找其全部占场记录 |
| `activity(status, start_time)` | 已发布活动列表、审核队列 | 按状态和时间读取活动 |
| `registration(activity_id, status)` | 报名人数统计、成员列表 | 统计某活动有效报名 |

### 4.3 时间区间冲突查询

新预约区间为 `[newStart, newEnd)`；已有预约区间为 `[start_time, end_time)`。

两个区间重叠的条件：

```sql
start_time < :newEnd
AND end_time > :newStart
```

查询同一球场的有效冲突：

```sql
WHERE court_id = :courtId
  AND status = 1
  AND start_time < :newEnd
  AND end_time > :newStart
```

首尾相接不算冲突。例如 `19:00–20:00` 与 `20:00–21:00` 可以同时存在。

### 4.4 联合索引的基本判断

设计联合索引时优先考虑真实查询条件：

1. 先放高频的等值过滤字段；
2. 再放范围查询字段；
3. 不为了“字段看起来全”而随意加列；
4. 每新增一个索引，都要考虑写入成本与维护成本。

本项目预约冲突查询先按 `court_id = ?` 精确定位球场，再按 `start_time` 做时间范围筛选，所以以 `court_id` 开头。

### 4.5 索引不能解决什么

普通索引不能阻止两个用户同时写入冲突预约；唯一索引也无法完整表达“两个任意时间区间不重叠”。

```text
19:00–21:00
20:00–22:00
```

两条记录字段不完全相同，唯一索引不会拒绝，但它们业务上冲突。此问题必须由 Service 的区间检查、事务和锁处理。

## 5. 事务、锁与并发设计

### 5.1 事务的边界

同一个业务动作中，必须“要么都成功、要么都失败”的数据库操作放入同一事务。

| 业务动作 | 同一事务内的关键动作 |
|---|---|
| 创建个人预约 | 校验后锁用户/球场、查冲突、写 reservation |
| 创建活动 | 锁全部目标球场、查冲突、写 activity、写 N 条 reservation、写创建者 registration |
| 驳回/取消活动 | 改 activity 状态、取消活动占场、取消活动报名 |
| 报名活动 | 锁活动、查状态和人数、写入或恢复 registration |

### 5.2 锁解决的不是“查询快”，而是“并发正确”

当“先查再写”会被其他请求插队时，必须在事务内锁住需要保护的对象。

```text
错误窗口：查到还有名额 → 另一个请求也查到还有名额 → 两人都写入
正确思路：锁活动 → 检查人数 → 写报名 → 提交事务释放锁
```

本项目的预定锁顺序：

```text
user → court（按 court_id 升序）→ activity
```

统一顺序的目的是降低多个事务互相等待形成死锁的概率。

### 5.3 当前已知风险

预约模块已有并发超卖回归用例。已确认的问题是：在 MySQL `REPEATABLE READ` 隔离级别下，事务内前置的普通查询可能固定快照，使得获得球场行锁后仍读到旧数据。

该问题尚未修复。后续必须先复现、理解快照读与当前读，再选择并验证修复方案；不能仅因为“代码有 `FOR UPDATE`”就认为并发安全。

## 6. 后端实现规范

### 6.1 分层职责

```text
Controller：接收请求、参数校验、返回统一响应；不承载核心业务。
Service：业务规则、权限、事务、状态流转、并发控制。
Mapper：数据库读写；SQL 与业务意图一一对应。
Entity/DTO/VO：分别承载持久化对象、请求参数、返回数据。
```

### 6.2 写接口的最小检查清单

实现一个写接口前，确认：

1. 是否需要登录、角色或资源归属校验？
2. 输入是否合法？时间、状态、数量边界是否校验？
3. 是否会修改多张表？若会，是否需要事务？
4. 是否存在重复点击或网络重试？幂等语义是什么？
5. 是否存在并发写入？需要锁定什么对象？
6. 失败后是否会留下半完成数据？
7. 是否已有单元、集成或并发测试覆盖关键规则？

### 6.3 状态字段规范

- 状态转换必须由 Service 控制，不让前端任意传目标状态。
- 不把“满员”“过期”等可从数据或时间推导的状态随意落库。
- 不做物理删除时要有明确业务理由；本项目活动用状态流转保存生命周期。
- 取消报名/预约使用状态变更而非删除时，要配合唯一约束与重新激活逻辑。

### 6.4 API 与安全底线

- 后端必须做权限校验；前端隐藏按钮不是安全控制。
- 密码只存 BCrypt 等哈希，不存明文。
- 统一错误码和异常处理，避免不同接口对同类错误返回不同语义。
- 所有日期时间以服务端为准；前端时间只作为输入。
- 配置中的密码、JWT 密钥等敏感数据在部署前必须改为环境变量注入。

## 7. 测试与验证规范

| 类型 | 要证明什么 | 本项目例子 |
|---|---|---|
| 单元测试 | 纯规则、边界条件 | 整点校验、连续占用两小时判断 |
| 集成测试 | Service、Mapper、MySQL 共同工作正确 | 创建/取消预约、活动状态流转 |
| 并发测试 | 多请求同时执行时仍满足业务不变量 | 同一时段只能有一个预约成功、最后一个名额不超卖 |

修复 Bug 的顺序：先稳定复现 → 找根因 → 加/保留失败测试 → 最小修复 → 跑相关回归测试。

不能因为某条测试暴露严重缺陷就删除它；应保留为长期回归守卫。

## 8. 面试表达模板

### 8.1 介绍数据模型

> 我把活动、场地占用和报名拆成三类事实：`activity` 管活动本身，`reservation` 作为统一场地占用账本，`registration` 管用户参与关系。一个活动可占多块场地，因此通过多条 reservation 关联，而不是在 activity 中存场地数组；活动报名人数则由 registration 的有效记录统计得出。

### 8.2 介绍数据库与 Service 的边界

> 能精确用单行约束表达的规则，例如用户名唯一、一人一活动一条报名，我使用唯一约束做数据库兜底。时段冲突、报名满员、活动取消后的跨表状态变化属于跨行或跨表规则，由 Service 放在事务中处理；并发场景再结合锁保证检查和写入的正确性。

### 8.3 介绍预约冲突判断

> 我把场地占用统一记录为时间区间。新旧区间在 `newStart < oldEnd && newEnd > oldStart` 时判为重叠；首尾相接不冲突。查询使用 court_id 与时间的联合索引缩小扫描范围，但索引本身不防超卖，最终仍需由事务和并发控制保证。

### 8.4 面试自检问题

1. 为什么活动不直接存 `court_id`？
2. 为什么 reservation 不用 `type` 字段区分个人和活动占场？
3. 普通索引、唯一索引、外键分别解决什么问题？
4. 为什么区间冲突不能完整由唯一索引解决？
5. 为什么活动创建、占场、创建者报名必须放在同一个事务？
6. 如果两个用户同时抢最后一个名额，怎样避免超卖？
