# 前端设计规范 · Badminton Community

> 本文是前端视觉与交互的**唯一规范源**。Phase 2–4 的所有实现以此为准。
> 创建于 Phase 1（现状勘察），状态：**已定稿，待落地**。
>
> 约束前提：**不改后端**。不改 API、数据库、业务逻辑、接口字段、权限。

---

## 0. 一句话定位

> 这不是「羽毛球管理系统」，是 **「帮你找到下一场球」**。

三个核心动作：**发现球局 → 加入球局 → 发起球局**。
场地预约是"没有合适球局时自己开局"的兜底动作，**不再是产品入口**。

判断标准：用户打开后前 3 秒应该知道"我该看哪里、我该做什么"。
最终目标：**去掉项目名称，别人看到截图也会认为这是一个真实创业产品。**

## 1. 现状勘察（Phase 1 结论）

### 1.1 技术栈

| 层 | 现状 |
|---|---|
| 框架 | Vue 3.5，Composition API + `<script setup>` |
| 构建 | Vite 6 |
| 路由 | Vue Router 4，hash 模式 |
| 状态 | Pinia（仅 1 个 store：`user`） |
| UI 库 | Element Plus 2.14，**全量引入** |
| HTTP | axios + 响应拦截器（统一处理 `code === '0'`） |
| 语言 | 纯 JavaScript，无 TypeScript |
| 样式 | 1 个全局 `styles.css` + 各页 `<style scoped>` |
| 图片资源 | **零**（无任何图片 / svg 文件） |

### 1.2 结构性根因

**这个项目没有首页。** `router/index.js:26` 中 `/` 直接 `redirect: '/venues'`。

用户登录后第一眼看到的是 `reservation` 表的排期视图（8:00–22:00 时段网格）。
**产品第一个画面就是数据库视图 —— 这是"像后台系统"的根因，不是配色问题。**

导航五项完全平级（场馆预约 / 我的预约 / 活动 / 社区 / 我的），无主次。

**`src/` 下没有 `components/` 目录 —— 零个可复用组件。** 11 个页面各自重写标题区、
元信息行、列表、空状态。这是"所有元素视觉权重一样"的结构性原因。

| 组件 | 用量 |

| `el-table` 系 | 18 |
| `el-button` | 24 |
| `el-icon` | 14（多为贴字前的装饰，无信息作用） |
| `el-card` | 10 |
| `el-tag` | 10 |
| **`el-empty`** | **4 页**（默认灰色方块插画） |

### 1.4 视觉问题（含证据）

| # | 问题 | 证据 |
|---|---|---|

| 2 | 紫蓝渐变 + 白圆角卡 + 每卡同一层阴影 | "SaaS-card kit" |
| 3 | 圆角 / 阴影无层级 | 全站 20 处 `border-radius` 声明，绝大多数为 10px |
| 4 | 空状态是默认插画 | 4 个页面 |
| 5 | 卡片网格低数据量崩坏 | `auto-fill minmax(280px,1fr)`，1 条活动时拉伸成 1080px 全宽白板 |
| 6 | 标题没有力量 | 页面标题 20px/600，与正文仅差 6px |
| 7 | 空洞的营销句式副标题 | "找一个球局加入，或者自己发起一场" ×3 处 |

### 1.5 UX 问题（按严重度）

1. **活动卡片无法回答"我能不能去"。** 字段顺序为 标题 → 状态 → 时间 → 发起人 → 进度条，
   **最影响决策的"还差几人 / 是否已满"放在最底下**，形式是 6px 细进度条 + 12px 灰字。
   且**列表页没有任何加入按钮**，必须点进详情。
2. **CTA 主次颠倒。** `ActivityDetail.vue:124` 第一个按钮是「返回列表」（系统导航），
   而「加入球局」在 184 行，被压在一堆描述字段下面。
3. **把后端实现讲给用户**（5 处 `el-alert`）。例：`Profile.vue:108`
   —— "只填昵称时头像保持不变（**后端语义为「不提供的字段不改动」**）"。
4. **个人主页是数据库记录视图。** `Profile.vue` 用 `el-descriptions` 展示
   用户名 / ID / 注册时间；换头像要求填图片 URL。而**后端本可支撑**
   "打过几场 / 发起过几局 / 有哪些球友"——一个都没用。
5. **没有"下一场球"概念。** 全站没有任何地方回答"我最近的一场球是什么时候"。

### 1.6 最像 AI 生成的 8 个特征

1. 紫蓝渐变底 + 白圆角卡 + 统一阴影
2. `el-empty` 默认插画（4 页）
3. `el-tag` 状态胶囊按颜色编码成一套（10 处）
4. 卡片网格套在任何元素表上
5. **每个页面骨架完全一致**：`page-head → 卡片区 → 分页`
6. `el-progress` 细横条当唯一数据可视化
7. 空洞的营销句式副标题
8. 图标当装饰贴字前（14 处）

### 1.7 最像后台系统的 7 个特征

1. `el-table` + 分页（我的预约）
2. `el-descriptions` + `border`（Profile / ActivityDetail）—— "数据库行详情"控件
3. `el-switch`「只看未来」—— 过滤条件像运营后台
4. 原始 ISO 时间字符串
5. `el-alert` 解释后端语义
6. 页面标题是**资源名**而非**用户目标**
7. 状态用 0/1/2/3/4 映射文案

### 1.8 保留清单（资产，不动）

| 资产 | 理由 |
|---|---|
| 后端 39 接口 + `Result` 信封 | 契约稳定，所有问题都能在展示层解决 |
| axios 拦截器统一判 `code === '0'` | 页面里无一处 `if (res.code)`，很干净 |
| 场馆预约的时间表网格 | 唯一已跳出卡片流的页面 |
| `styles.css` 令牌层 | **结构**（三级文字 / 三档圆角 / 变量化）保留；**色值**替换 |
| hash 路由 + `meta.public` 守卫 | 部署简单，逻辑清晰 |
| 3 个回归脚本 + 1 个截图脚本 | 改视觉时的安全网 |

## 2. 数据现实核查（决定方案能否落地）

| 设计诉求 | 现有数据 | 依据 / 处置 |
|---|---|---|
| 附近球局 / 距离 | ❌ 不能 | `VenueVO` 仅 `id/name/address`，**无经纬度** |
| 场地图片 / 活动封面 | ❌ 不能 | 无图片字段，项目零图片资源 |
| 球友水平 / 常打区域 | ❌ 不能 | `user` 仅 `id/username/nickname/avatarUrl/role/createTime` |
| 活动类型（单打/双打） | ❌ 不能 | 无 `type` 字段。**禁止用 `maxMembers` 硬猜**（会撒谎） |
| 活动在哪块场 | ⚠️ 详情可以，**列表不行** | 列表 VO `ActivityItemVO` 无 `courtIds`；按约束**不加字段** |
| 剩余名额 / 是否已满 | ✅ 能 | `maxMembers - joinedCount` |
| 报名球友 + 头像堆叠 | ✅ 能 | `ActivityMemberVO` 有 `nickname/avatarUrl` |
| 我打过几场 / 发起过几局 | ✅ 能 | 复用 `/activities/mine`、`/registrations/mine`、`/reservations/mine` |
| 今日 / 本周开打的球局 | ✅ 能 | `/activities` 的 `start_from` / `start_to` |

### 把缺口变成设计选择（不是缺陷）

**① 距离 → 时间。** 羽毛球是强时间偏好的运动（下班后、周末下午）。
把发现维度从**空间**换成**时间**：今天 / 明天 / 这个周末。
比距离更贴近真实决策，且诚实。

**② 零图片 → 排版驱动。** 视觉重量由**排版 + 大数字 + 几何图形**承担，不靠照片。
约束反而指向更高级的方向（Linear / Vercel 路径）。

## 3. 设计原则

1. **内容优先。** 每个元素必须回答"用户为什么需要看到它"，答不出就删。
2. **禁止 Card 堆叠。** 页面应混合：大标题区 / 列表 / 描边分隔 / 少量 Card / 留白 / 信息区块 / CTA / 数据展示，产生节奏。
3. **圆角分级。** 小 / 中 / 大按层级使用，**部分区域完全不用圆角**。
4. **描边优先于阴影。** 只有真正需要层次关系时才用阴影。
5. **一次只留一个主 CTA。** 一屏内至多一个品牌色按钮。
6. **高级感来自排版、留白、层级、对齐、节奏** —— 不来自渐变、阴影、圆角、玻璃、发光、粒子。

---

## 4. 视觉语言：三个属于我们的母题

1. **轨迹弧** —— 羽球被击出后的抛物线，这项运动最独特的形状。
   用于 Hero、区块分隔、空状态、加载态。
2. **场线** —— 细、精确、有方向的直线网格，作为**组织信息的手段**（非装饰）。
3. **大数字** —— "还差 2 人"。直接回答"我能不能去"，运动产品最有说服力的排版元素。

## 5. Design System 规格

### 5.1 色彩（对比度已实算并标注）

```css
--bg:        #F7F8F7;  /* 页面底，去蓝调近白 */
--surface:   #FFFFFF;  /* 面 */
--surface-2: #F1F3F2;  /* 次级面：表头、填充块 */

--ink:       #101311;  /* 主文字 / 深色区块底    对白 17.6:1 */
--ink-2:     #4B514D;  /* 次级文字               对底  7.6:1 */
--ink-3:     #666D67;  /* 元信息 / 辅助          对底  5.0:1 */

--line:      #E8EAE9;  /* 发丝描边（默认分隔手段） */
--line-2:    #D6D9D7;  /* 强调描边 */

--volt:      #C6F432;  /* 品牌色：仅用于填充。配 --ink 文字 = 14.6:1 */
--volt-600:  #5F7A10;  /* 品牌色文字版 = 4.9:1（仅少量使用） */
--volt-100:  #F2FBD8;  /* 品牌色浅底 */

--danger:    #C0392B;
--warn:      #9A6B12;
```

**硬规则**

- 荧光色在白底上对比度不足 3:1，**绝不能作为正文色**。
  品牌色的用法只有两种：① 按钮/徽标填充 + 深色文字；② 强调块/下划线。
- 需要"品牌色系文字"时用 `--volt-600`，且面积要小。
- 全站**不得出现渐变**（Hero 除外可用一层极简的深色块，非渐变）。

### 5.2 Typography

- **拉丁展示字体自托管**（`public/fonts/`，一个 woff2 ≈30KB）。
  `fonts.googleapis.com` 虽然可达但国内不稳定，**不能作为首屏依赖**。
- **中文不加载 webfont**（动辄 3–8MB），使用系统字体栈 + 字重/字号制造层级。

| 层级 | 字号 | 字重 | 说明 |
|---|---|---|---|
| Hero | 56–72px | 700 | 紧字距 `-0.02em`，行高 1.05 |
| Section | 22–28px | 600 | |
| 数据 | 32–40px | 600 | `font-variant-numeric: tabular-nums` |
| Body | 15–16px | 400 | 行高 1.6 |
| Metadata | 12–13px | 400 | `--ink-3` |

比价关系：**Hero 与 Body 的比值要达到 4× 以上**（当前是 1.25×）。

### 5.3 Spacing

8pt 基准：`4 / 8 / 12 / 16 / 24 / 32 / 48 / 64 / 96`。
区块之间用 48–96px 制造留白节奏，**不要所有间距都落在 16px**。

### 5.4 Radius

```css
--r-xs: 2px;   /* 表格、徽标、数字块 —— 接近直角 */
--r-sm: 6px;   /* 按钮、输入框 */
--r-md: 10px;  /* 卡片 */
--r-lg: 16px;  /* 唯一的大圆角，只给 Hero / 弹层 */
```

### 5.5 组件清单（Phase 2 建立，全部自研）

`AppButton`（primary / ghost / outline / danger，**仅 primary 用品牌色**）·
`AppInput` · `AppBadge`（5 态）· `AppCard`（仅在真正需要描边时使用）·
`AppAvatar` + 头像堆叠 · `AppNav`（桌面横向 / **移动底部 Tab**）·
`AppSheet`（替代 `el-dialog`）· `AppToast` · `AppSkeleton` ·
`EmptyState`（替掉 4 处 `el-empty`）· `StatNumber` · `CourtGrid`（从 Venues 抽出）·
`RallyArc`（轨迹弧 SVG）· `ActivityRow`（活动行，首页与列表共用）

**边界**：Element Plus **只保留交互型组件**（Select / DatePicker / Dropdown /
Pagination 等行为复杂者）。**展示型组件全部自研**（Button / Card / Tag / Avatar /
Empty / Progress）—— 这是摆脱后台感的物理手段。

### 5.6 🔴 组件类名必须带命名空间

**根类名一律加 `app-` / 业务前缀**（`act-row`、`app-field`、`app-btn`…）。

原因（踩过的坑）：Vue 的 scoped 样式会把**父组件的 scope 属性加到子组件的根元素上**。
所以父页面里一条 `.row { display: flex }` 会直接命中子组件的根元素，
把组件自己的 `display: grid` 打掉 —— **而且不报任何错**，只是布局莫名其妙塌了。

**已命名空间化的**：`ActivityRow`（`.act-row*`）、`AppInput`（`.app-field*`）。
**待处理**：`AppButton`（`.btn`）、`AppBadge`（`.badge`）、`AppAvatar`（`.avatar`）、
`StatNumber`（`.stat`）、`RallyArc`（`.arc`）、`AppSkeleton`（`.sk`）。
这些名字都是页面级常见词，**在给用到它们的页面写样式前必须先改名**。

验证手段：改完类名后，用无头浏览器 `getComputedStyle` 打印
`display` / `gridTemplateColumns` 和三个子元素的 `getBoundingClientRect()` ——
**光看截图看不出网格列宽是否正确**（本次就是靠探针才第二次发现模板 class 没跟着改）。

## 7. 逐页重做方向

| 页面 | 现在的问题 | 重做后的核心结构 |
|---|---|---|
| **首页（新建）** | 不存在 | Hero（品牌 + 主 CTA）→ **今天 / 明天开打的球局**（横向 3–4 张）→ 本周热门 → 场地入口（一组，非卡片墙）→ 社区精选 → 发起球局 CTA |
| **活动列表** | 全宽白板、无加入按钮、时间未格式化 | **按时间分组的列表流**（今天 / 明天 / 周末）；每行左侧大数字时间，右侧**剩余名额**；"还差 2 人"直接可点加入 |
| **活动详情** | CTA 埋在描述下、返回键在顶部 | **加入球局做成固定操作栏**（滚到哪都在）；首屏直接给 时间 + 姓名 + 名额 + 头像堆叠 |
| **场地与预约** | 时间表已对，但仍是数据表 | 保留时间表网格；上方加**场地身份区**（名称 / 地址 / N 片场 / 今日空闲）；空状态用轨迹弧 |
| **社区** | `el-empty` + 卡片流 + 点赞数 | 改成**动态流**（人 + 动作 + 时间）。保留发帖与评论；**不加速藏 / 关注**（不符合当前定位） |
| **球员档案** | 用户名 / ID / 注册时间 | 头像 + 昵称 + 入会时间 + **打过 N 场 / 发起 N 局 / 常去 X 球馆**（全部可算）+ 两个 tab（我发起的 / 我参加的）+ 编辑资料收进次要入口 |
| **登录 / 注册** | 登录已重做，注册仍是旧风格 | 统一到新令牌 |

**活动行的信息设计（回答"我能不能去"）**

```
时间（大数字）  球局标题                        还差 2 人  [加入]
周四 17:00      周五晚双打约战                  ██████░░   或
2 小时          小林发起 · 已报 6 人                        已满
```

权重顺序：**时间 > 剩余名额 > 标题 > 发起人**。
人数到达上限时整行降权并标注"已满"，不给按钮。

## 8. 响应式与动效

**响应式不是缩小版。** 断点：`375 / 768 / 1024 / 1440`。

- 移动端：导航改**底部 Tab**；活动行改纵向堆叠，"还差 2 人"移到大字位置；
  桌面右侧的操作按钮移到底部固定栏。
- 禁止横向滚动。触控目标 ≥ 44px。

**动效只保留 4 种**：hover 反馈（120–160ms）、按钮按下、页面切换淡入（150ms）、
Skeleton 占位。**不做**飞入 / 粒子 / 发光 / 大幅缩放 / 炫技动画。
`prefers-reduced-motion` 必须被尊重。

- **新增 `src/utils/datetime.js`** —— 全站唯一的时间解析入口。
  改造前 `Home.vue` 与 `ActivityRow.vue` 各有一份重复实现，每加一个列表页就要抄第三份。
  内含两个踩过的坑：日期差只比年月日；不用 `new Date(str)`（后端串带 `T`/不带 `T` 两种）。
- **排序**：后端 `ORDER BY start_time DESC` 对发现型列表是反的，前端重排
  （未结束升序在前、已结束降序垫底）。**后端未改**。
- **用「加载更多」替代分页器**：分页会把同一个时间分组切到两页，分组就失去意义。
- `ActivityRow` 新增 `state="past"`：已结束的球局不再显示"还差 N 人"（没有名额可抢），
  改为明确的「已结束」并把整行降级。
- `StatNumber` 新增 `label-position="before"`：中文「还差 7 人」是固定语序，
  标签放下一行会被读成「7 人 / 还差」，得从下往上读。
- **导航 5 项 → 4 项**（首页 / 球局 / 场地 / 社区），「我的预约」收进用户菜单。
  5 个平级入口是"所有模块视觉权重一样"的结构性来源；移动端底部 Tab 4 项也正好
  是拇指操作最舒服的数量。

### Phase 3 已落地的事实（供 Phase 4 对齐）
- `/` → `/home`，`/home` 是首页路由；catch-all 也指向 `/home`；登录后默认跳 `/`。
- 导航新增「首页」（用自绘 `isActive` 判断高亮 —— `to="/"` 的 RouterLink 其
  `router-link-active` 对所有路径都成立，不能直接用）。
- 首页区块：Hero（`FIND YOUR GAME.`）→ 轨迹弧分隔 → 今天开打 → 接下来几天 → 场地 → 球友在聊。
- **首页只有 2 个按钮**（Hero 的主/次 CTA）。列表行刻意**不放「加入」按钮**：整行可点进详情，
  加入动作归详情页 —— 一屏六行六个按钮就是"按钮过多"的典型症状。
- ⚠️ **后端公开列表是 `ORDER BY start_time DESC`（最新发布在前）**。
  "接下来几天"这种发现型列表必须**在展示层重排为升序**（`sortByStartAsc`）。
  Phase 4 的球局列表同样要处理。
