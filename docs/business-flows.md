# 业务动作流程设计

> 本文档把 `database.md` 中「由 Service 层负责的规则」落实为 15 个核心业务动作的**可执行流程**，是后端实现（Service/事务/并发）的依据。
>
> 关联文档：[需求分析](requirements.md) · [数据库设计](database.md) · [技术决策记录](decisions.md)
>
> 约定：本文件只描述流程与规则，不写 Java、不写 SQL、不新增表、不引入额外机制。

## 0. 全局约定

### 0.1 角色与状态（与 database.md 一致）

| 对象                  | 枚举                            |
| ------------------- | ----------------------------- |
| user.role           | 0=普通用户，1=管理员                  |
| court.status        | 1=可预约，2=不可预约                  |
| activity.status     | 0=待审核，1=已发布，2=已驳回，3=已取消，4=已结束 |
| reservation.status  | 1=有效，2=已取消                    |
| registration.status | 1=已报名，2=已取消                   |

### 0.2 归属与冲突统一规则（全局最优先）

- `reservation` 是**唯一**场地占用账本。个人预约：`user_id` 有值、`activity_id` 为空；活动占场：`activity_id` 有值、`user_id` 为空。两者至多一者非空。
- **个人预约与活动占场走同一套冲突检查**：同一球场、区间相交、双方都是 `status=1`（有效），即视为冲突，无论来源。
- 冲突查询条件（两个区间相交）：`新.start_time < 已有.end_time AND 新.end_time > 已有.start_time`。
- 球场是否已被占用，只由该球场上「有效」的 reservation 行决定；已取消行不参与冲突。

### 0.3 时间与窗口约定

- 预约/活动时间以**整小时**为粒度：分钟、秒必须为 0。
- 单个 reservation / activity 区间默认**不允许跨自然日**（如 23:00–01:00 不支持，见附录假设 4）。
- **7 天开放窗口**（requirements 规则 5、17）：允许预约当天起未来 7 个自然日内、且**尚未开始**的时段（目标时段开始时间晚于当前时刻，即不允许预约已经开始或已过去的时段）。个人预约与活动占场**同等适用**，任何写入 reservation 的路径都必须先通过此校验。
- 取消窗口：个人预约剩余时间 ≥ 4 小时可自行取消（`now ≤ start_time - 4h`）；不足 4 小时普通用户不可自行取消。
- 时间统一以服务器时间为准。

### 0.4 通用并发策略（不引入新机制）

只用现有表的主键行做**悲观锁**（排他行锁），全部冲突路径遵循统一加锁顺序：

1. 涉及「个人重叠上限 ≤2」的写入：先锁 `user` 行。
2. 任何涉及场地占用写入（个人预约、活动创建锁场）：按 `court_id` **升序**逐场加锁后再做冲突检查。
3. 报名/取消报名涉及满员：先锁 `activity` 行。
4. 固定加锁顺序（user → court 升序 → activity），避免死锁。规定顺序 避免死锁
5. 所有「检查 + 写入」必须在**同一个事务**内完成。

锁的粒度说明：以球场行为锁串行化「该球场的写入」在 MVP 流量下足够，且不新增表。

### 0.5 业务错误清单（文案可作为统一错误码的取值来源）

| 错误              | 说明                     |
| --------------- | ---------------------- |
| 用户名已存在          | 注册重名                   |
| 用户名或密码错误        | 登录失败                   |
| 时间不合法           | 非整点 / end ≤ start / 跨天 |
| 超出 7 天预约窗口      | 目标时段在窗口外（含活动锁场）        |
| 球场不存在或不可预约      | court.status=2         |
| 球场已被预约          | 与有效行冲突                 |
| 超过个人预约数量限制      | 重叠有效个人预约已达 2           |
| 预约不存在 / 不是本人预约  | 取消时校验                  |
| 超过 4 小时取消限制     | 开场前不足 4h 普通用户不可自取消     |
| 活动不存在           |                        |
| 活动状态不允许该操作      | 通用：状态不匹配               |
| 活动未发布           | 报名时 activity.status≠1  |
| 报名窗口已关闭         | 已开始或已结束                |
| 活动已满员           | 报名数已达 max_members      |
| 已报名该活动 / 未报名该活动 | 报名/取消报名重复操作            |
| 无权限             | 非创建者/非管理员              |
| 场地存在未来有效预约，禁止停用 | 球场管理                   |

## 动作 1：用户注册

**触发者**：匿名访客。

**前置条件**：无。

**核心流程**

1. 校验参数：username 非空且未被占用、password 满足最小强度、nickname 非空。
2. 对 password 做哈希（如 BCrypt），生成 `password_hash`。
3. 插入 user 行：`role=0（普通用户）`、`avatar_url=NULL`。

**事务边界**：单条插入，一个事务即可。

**并发控制**：存在并发注册同名。`username` 有唯一索引兜底——两个请求同时插入同名，一个成功、一个抛唯一约束错误，捕获后转为「用户名已存在」返回。

**状态变化**：无业务状态（新建一行 role=0 的用户）。

**失败情况**：用户名已存在；参数不合法。

**结果**：新增一行普通用户；密码只以哈希形式入库。

---

## 动作 2：用户登录

**触发者**：未登录用户。

**前置条件**：用户已注册。

**核心流程**

1. 按 username 查询用户。
2. 校验 `password_hash` 与输入是否匹配。
3. 匹配成功则签发会话凭据（Session 或 JWT——**机制待 ADR 决策**，本流程不依赖具体实现）。

**事务边界**：无数据库写入（纯查询 + 凭据签发）。

**并发控制**：无。

**状态变化**：无。

**失败情况**：用户名或密码错误（不区分提示，避免账号枚举）。

**结果**：返回会话凭据，后续动作以该用户身份执行。

## 动作 3：用户创建个人球场预约

**触发者**：登录用户。

**前置条件**

- 目标球场存在且 `court.status=1`（可预约）。
- 目标时段满足：整点、end>start、不跨天、落在 7 天窗口内。

**核心流程**

1. 时间与窗口校验（0.3）。
2. 加载并**锁 user 行**（排他锁）——串行化同一用户并发的预约写入。
3. 统计该用户「重叠的**有效个人预约**」数量：`user_id=我 AND activity_id IS NULL AND status=1`，与本次时段区间相交的行数。若 ≥2 → 失败「超过个人预约数量限制」。注意：**只统计个人行，活动占场行不计入**（活动占场 user_id 为空，天然不会命中）。
4. 校验「同一天同一球场累计占用 ≤ 2 小时」（requirements 规则 18）：查询该用户当天（`start_time` 落在自然日内）在同一球场 `court_id=目标场 AND user_id=我 AND activity_id IS NULL AND status=1` 的全部有效行，与本次时段一起按时间排序，**把重叠或首尾相接的时段合并成连续段**；若任一段的跨度 > 2 小时 → 失败「同一天同一球场累计占用超过 2 小时」。恰好 2 小时（如 19:00–21:00）允许；中间有空档的两段不合并。
5. 按 `court_id` **锁球场行**（排他锁）。
6. 对该球场执行**统一冲突检查**：查询该场 `status=1` 的有效行（含个人与活动来源）与本次时段相交者。存在 → 失败「球场已被预约」。
7. 插入 reservation 行：`user_id=我, activity_id=NULL, court_id, start_time, end_time, status=1`。

**事务边界**：步骤 2–7 必须在**同一个事务**内。先检查后插入，中间不允许提交。

**并发控制**

- 存在（场景 A）：两个用户同时抢同一球场同一时段。
- 保护数据：该球场时段的有效占用行；以及本人的重叠预约计数。
- 锁：user 行锁（步骤 2）+ court 行锁（步骤 5）。两个事务对同一球场串行：后者等锁释放后重查冲突 → 发现有效行 → 失败「球场已被预约」。
- 避免重复占用：冲突检查与插入同事务 + 球场行锁，保证「检查后、插入前」不会有第三方写入同一球场。
- 规则 18 的累计占用检查放在 user 行锁内（步骤 4）：同一用户的并发创建被 user 行锁串行化，不会出现两人「同时各订一小时、合计超 2 小时却都通过」的情况。

**状态变化**：新增一条 `status=1` 的个人 reservation。

**失败情况**：时间不合法 / 超出 7 天窗口 / 球场不存在或不可预约 / 球场已被预约 / 超过个人预约数量限制 / 同一天同一球场累计占用超过 2 小时（requirements 规则 18）。

**结果**：插入一条有效个人占用行；该球场该时段对其他预约（含活动锁场）关闭。

## 动作 4：用户取消个人球场预约

**触发者**：该预约的本人（`user_id=自己`）。

**前置条件**

- 目标 reservation 存在、`activity_id IS NULL`（个人行）、`status=1`。
- 剩余时间 ≥4 小时：`now ≤ start_time - 4h`。

**核心流程**

1. 定位 reservation 行并校验归属与状态。
2. 校验取消窗口。
3. 更新该行：`status=2（已取消）`、`cancel_time=now`。

**事务边界**：单条带条件更新即可。

**并发控制**

- 存在：重复点击取消 / 与系统（管理员）取消并发。
- 用条件更新（`WHERE ... AND status=1`）保证幂等：第二次执行影响 0 行 → 按「已取消」处理，不报错。

**状态变化**：reservation 行 `1 有效 → 2 已取消`，并记录 cancel_time。该球场时段随即自动重新开放（冲突检查只数有效行）。

**失败情况**：预约不存在 / 不是本人预约 / 已取消 / 超过 4 小时取消限制（普通用户不可自行取消；管理员特殊取消为独立路径，不受此限制——requirements 规则 11）。

**结果**：占用行置为已取消；时段空出；无级联对象（个人预约不关联报名）。

## 动作 5：用户创建羽毛球活动

**触发者**：登录用户（普通用户与管理员均可）。

**前置条件**

- 提交：title、description、start_time/end_time、max_members（≥1）、球场 id 列表（≥1 块场）。
- 时段满足：整点、end>start、不跨天、**落在 7 天窗口内**（规则 17：活动锁场与个人预约同窗口）。
- 所有目标球场存在且 `court.status=1`。

**核心流程**

1. 参数、时间、窗口校验。
2. 加载并**按 court_id 升序逐块锁球场行**。
3. 对每块球场执行**与个人预约完全相同的统一冲突检查**（查该场有效行，含个人与活动来源）。任一块冲突 → 整体失败，返回第一块冲突的场与时段。
4. 插入 activity 行：`creator_id=我, status=0（待审核）`。
5. 为每块球场插入一条 reservation：`activity_id=新活动, user_id=NULL, start_time/end_time=活动区间, status=1`。
6. 插入创建者 registration：`user_id=创建者, activity_id=新活动, status=1`（**创建者自动成为第一名报名者**，占用 1 个名额，故 max_members ≥1 校验在第 1 步）。

**事务边界**：步骤 2–6 **全部在同一事务**。任一步失败（含某块场被抢）整体回滚——不允许出现「活动建了但只锁到一半球场」。

**并发控制**

- 存在（场景 C）：创建活动锁场的同时，另一用户正在预约其中一块场。
- 保护数据：多块球场的时段占用；活动/报名/占场三者的写入一致性。
- 锁：各球场行（升序）。与动作 3 共用同一把球场锁与同一冲突规则 → 两事务串行，后到者重查冲突后失败（活动创建失败 或 个人预约失败），不会重复占用。
- 死锁规避：涉及多球场的写入一律按 `court_id` 升序加锁。

**状态变化**

- activity：新建 `0 待审核`；
- reservation：新增 N 条 `1 有效` 活动占场行（**待审核期间即占用球场**，这是既定业务，审核时会释放或保留）；
- registration：新增创建者 1 条 `1 已报名`。

**失败情况**：时间不合法 / 超出 7 天窗口 / 球场不存在或不可预约 / 球场已被预约（部分冲突则整体失败）/ max_members<1。

**结果**：一条待审核活动 + N 条有效活动占场 + 创建者报名行，全部一致落库。

## 动作 6：管理员审核活动

**触发者**：管理员（`role=1`）。

**前置条件**：目标 activity 存在且 `status=0（待审核）`。

**核心流程（通过）**

1. 定位 activity，校验状态。
2. 更新：`status=1（已发布）`、`reviewer_id=管理员`、`review_time=now`。
3. 其 reservation（活动占场）与 registration（创建者报名）**保持原状**。

**核心流程（驳回）**

1. 定位 activity，校验状态。
2. 更新：`status=2（已驳回）`、`reviewer_id、review_time、reject_reason`。
3. **同事务**释放占场：该活动名下所有 `status=1` 的 reservation 行 → `status=2`、`cancel_time=now`。
4. **同事务**取消报名：该活动名下所有 registration 行 → `status=2`（当前仅创建者）。

**事务边界**：通过 = 单行更新；驳回 = 活动 + N 条 reservation + registration 的**多表同一事务**。

**并发控制**

- 存在：重复审核 / 与「创建者取消活动」并发。
- 用条件更新（`WHERE status=0`）保证只处理一次：影响 0 行 → 返回「活动状态不允许该操作」。

**状态变化**

- 通过：activity 0 → 1；占场与报名不变。
- 驳回：activity 0 → 2；占场全部 1 → 2；报名全部 1 → 2。

**失败情况**：活动不存在 / 非待审核状态（已被处理）/ 无权限。

**结果**：通过 → 活动可被报名、占场生效；驳回 → 场地全部释放、名额作废。

## 动作 7：用户报名活动

**触发者**：登录用户。

**前置条件**

- activity 存在且 `status=1（已发布）`。
- 当前时间在活动开始之前（报名窗口，见附录假设 1）。
- 用户不是重复报名。

**核心流程**

1. 定位 activity 并**锁 activity 行**（排他锁）。
2. 校验状态（仍为 1）与报名窗口。
3. 统计 `user_id=该用户 AND activity_id=该活动 AND status=1` 的 registration 行数：
   - 已有有效行 → 返回「已报名该活动」（幂等成功，不重复计）。
   - 仅存在 `status=2` 的历史行 → 走「重新报名」：将该行状态置回 1（不新增行，遵守 `(user_id, activity_id)` 唯一）。
   - 无任何行 → 新建 registration 行 `status=1`。
4. 满员校验：统计该活动 `status=1` 的 registration 总行数（含创建者），必须 `< max_members`；否则失败「活动已满员」。

**事务边界**：步骤 1–4 同一事务。满员判定（步骤 4）依赖步骤 1 的 activity 行锁保证并发正确。

**并发控制**

- 存在（场景 B）：两个用户同时抢最后一个名额。
- 保护数据：该活动的报名计数（= status=1 行数）。
- 锁：`activity` 行排他锁——所有报名对同一活动串行，后到者在锁释放后重算名额，发现已满 → 失败「活动已满员」。不会超卖。
- 数据库兜底：`(user_id, activity_id)` 唯一约束拦截任何重复行。

**状态变化**：新增/恢复一条 `1 已报名` 的 registration。

**失败情况**：活动不存在 / 活动未发布 / 报名窗口已关闭 / 活动已满员 / 无权限。满员后再次成功报名不可能（前端隐藏按钮只是体验，真正的防线在第 1 步的锁 + 第 4 步计数）。

**结果**：该活动有效报名数 +1；达到 max_members 时系统不存任何「满员」状态，由查询推导。

## 动作 8：用户取消报名

**触发者**：已报名用户。

**前置条件**

- registration 存在且 `status=1`、`user_id=自己`。
- 活动尚未结束（`status≠4`）。若活动已被取消/驳回，报名由系统级联置为已取消，本动作不适用。

**核心流程**

1. 定位 registration，校验归属与状态。
2. 条件更新该行：`status=2（已取消）`（更新 update_time）。

**事务边界**：单条条件更新。**不需要**锁 activity 行——见并发控制说明。

**并发控制**

- 存在：取消报名与「其他人报名最后一个名额」并发。
- 分析：满员判定以 activity 行锁串行；取消报名不抢该锁，只会造成两种安全结果——(a) 计数读到取消前状态 → 保守拒绝新报名；(b) 取消先提交 → 空出名额可被使用。**两种方向都不会超卖**，因此不加锁是安全取舍。若实现方希望行为严格可预期，也可以让取消报名同样锁 activity 行，代价是增加一处串行。

**状态变化**：registration `1 → 2`，名额随之释放。

**失败情况**：未报名该活动 / 已取消 / 活动状态不允许（已结束、已取消、已驳回）。

**结果**：该用户报名行置为已取消；再次报名走动作 7 的「重新报名」分支，不产生第二行。

## 动作 9：活动创建者取消活动

**触发者**：该活动的创建者（`creator_id=自己`）。

**前置条件**

- activity 存在、`creator_id=自己`。
- `status ∈ {0 待审核, 1 已发布}`，且当前时间在活动开始之前（见附录假设 2）。

**核心流程**

1. 定位 activity 并**锁 activity 行**。
2. 校验创建者归属与状态。
3. 更新活动：`status=3（已取消）`。
4. **同事务**释放占场：名下所有 `status=1` 的 reservation 行 → `2 已取消`、`cancel_time=now`。
5. **同事务**取消报名：名下所有 registration 行 → `2 已取消`（含创建者本人）。

**事务边界**：活动 + N 条 reservation + 报名行，**同一事务**全部更新。

**并发控制**

- 存在：与管理员审核、管理员取消活动并发。
- 锁：activity 行。先到者成功，后到者重查状态发现非 `{0,1}` → 「活动状态不允许该操作」。

**状态变化**：activity 0/1 → 3；占场全部 1 → 2；报名全部 1 → 2。

**失败情况**：活动不存在 / 非创建者 / 状态不允许（已驳回、已结束、已取消）/ 已开始不允许取消（附录假设 2）/ 无权限。

**结果**：活动取消，场地全部释放回可约池，报名全部作废。

## 动作 10：管理员取消活动

**触发者**：管理员。

**前置条件**

- activity 存在且 `status ∈ {0 待审核, 1 已发布}`。
- 管理员不受「未开始」限制——可在特殊情况下取消（含已开始但未结束的活动，与 requirements 规则 11 精神一致）。

**核心流程**：与动作 9 相同，仅触发者变为管理员：

1. 锁 activity 行 → 2. 校验状态 → 3. `status=3` → 4. 释放全部占场 → 5. 取消全部报名，同一事务。

**事务边界**：同动作 9。

**并发控制**：同动作 9（activity 行锁，幂等条件更新）。

**状态变化**：activity → 3；占场 → 2；报名 → 2。

**失败情况**：活动不存在 / 状态不允许（已驳回、已结束、已取消）/ 无权限。

**结果**：同动作 9，由管理员发起。

## 动作 11：活动结束

**触发者**：系统（定时任务，或在查询活动列表/详情时懒更新）。

**前置条件**：`status=1` 且 `end_time ≤ now`。

**核心流程**

1. 批量条件更新：`UPDATE ... SET status=4 WHERE status=1 AND end_time ≤ now`（幂等：重复执行影响 0 行）。
2. 已结束活动的 reservation 占场行**保持 `status=1` 不动**——是否过期由 `end_time < now` 推导，不引入「已完成」状态（database.md 约定）。
3. registration 行也**保持原状**——「已报名」在结束后作为历史事实保留。

**事务边界**：单条批量条件更新。

**并发控制**：与报名并发时，报名要求 `status=1` 且未开始；结束动作与报名都会触碰 activity 状态，靠条件更新幂等，不会互相破坏。

**状态变化**：activity 1 → 4。

**失败情况**：无（无业务失败，未满足条件则无事发生）。

**结果**：活动进入终态；不可再报名/取消/修改；历史占场与报名保留可查。

## 动作 12：管理员管理球场

**触发者**：管理员。

**前置条件**：球场相关操作均有管理员权限。

**核心流程**

1. **新增球场**：在 venue 下插入 court 行，`status=1（可预约）`，名称在同场馆内唯一（唯一索引兜底）。
2. **修改球场名**：条件更新（同场馆重名 → 唯一约束报错）。
3. **置为不可预约**（`status: 1 → 2`）：  
   a. 锁该 court 行；  
   b. 检查是否存在「未来有效占用」：`court_id=该场 AND status=1 AND end_time > now`（个人与活动来源都算）。存在 → 拒绝「场地存在未来有效预约，禁止停用」，提示先处理预约；  
   c. 无 → 更新 `status=2`。
4. **恢复可预约**（`status: 2 → 1`）：直接更新。

**事务边界**：置为不可预约 = 锁 + 检查 + 更新同一事务；其余为单行更新。

**并发控制**

- 存在：停用球场与「正在写入该场预约」并发。
- 两方都锁 court 行 → 串行。停用方在锁释放后重查，若发现刚产生的新有效预约 → 拒绝停用；预约方在停用先提交后会发现 `court.status=2` → 拒绝预约。两个方向都安全。

**状态变化**：court.status 在 1/2 间切换。

**失败情况**：无权限 / 球场不存在 / 同场馆重名 / 存在未来有效预约时禁止停用。

**结果**：球场可约性受控；已存在的有效预约不受「改名」影响，也不会被「停用」越过。

## 动作 15：用户点赞 / 取消点赞

**触发者**：登录用户。

**前置条件**：目标 post 存在。

**核心流程**

1. **点赞**：插入 post_like 行 `(post_id, user_id)`；若已存在（复合主键冲突）→ 幂等返回「已点赞」，不报错。
2. **取消点赞**：删除该 `(post_id, user_id)` 行；若不存在 → 幂等成功。

**事务边界**：单行操作。

**状态变化**：post_like 行存在 / 不存在。

**失败情况**：帖子不存在。

**结果**：一人一帖至多一条点赞记录；取消后再次点赞允许（重新插入同一组合）。

## 附录 A：并发场景详析

### A. 两个用户同时预约同一个球场同一时间

**冲突点**：两事务都要往同一球场的同一时段写入有效占用行。

**锁顺序**：各自先锁自己的 user 行（互不冲突），随后**都锁同一 court 行**——第二个事务阻塞等待。

**结果**：

- 事务 1 获得球场锁 → 冲突检查无有效行 → 插入成功 → 提交释放锁。
- 事务 2 获得球场锁 → 重做冲突检查 → 发现事务 1 的有效行相交 → 失败「球场已被预约」。

**为什么不会重复占用**：冲突检查与插入在同一事务内，且球场行锁使「检查」与「任何新写入」互斥；不存在「两人都查到空、同时插入」的窗口。

**配套**：冲突查询必须命中索引 `reservation(court_id, start_time, end_time)`（database.md 第 5 节）。

### B. 两个用户同时报名活动的最后一个名额

**冲突点**：`status=1` 报名计数达到 `max_members` 的判断。

**锁顺序**：两个事务都**锁 activity 行**——串行。

**结果**：

- 事务 1 获得活动锁 → 计数 = max_members−1 → 报名成功 → 提交。
- 事务 2 获得活动锁 → 重数 = max_members → 失败「活动已满员」。

**为什么不会超卖**：满员判定与报名写入在同一事务内，且以 activity 行为锁；计数永远基于锁内最新已提交状态。

**配套兜底**：`(user_id, activity_id)` 唯一约束防止任何并发产生的重复行；创建者名额在第 5 步创建时即计入。

### C. 用户创建活动锁场时，另一用户同时预约相同球场与时间

**冲突点**：活动创建要写入 N 条活动占场行，个人预约要写入 1 条个人占场行，二者争夺同一球场的同一时段。

**两者共用同一把锁与同一条冲突规则**（database.md：统一占用账本，个人与活动无差别）：

| 先后       | 活动创建（动作 5）                                | 个人预约（动作 3）                        |
| -------- | ----------------------------------------- | --------------------------------- |
| 活动先拿到球场锁 | 冲突检查通过 → 插入活动行 + N 条占场 + 创建者报名 → 提交       | 等锁 → 重查发现活动占场行相交 → **失败「球场已被预约」** |
| 个人先拿到球场锁 | 等锁（若只冲突一块场）→ 重查发现个人有效行相交 → **活动创建整体回滚失败** | 插入个人占场 → 提交                       |

**要点**：

- 活动创建若跨多块场，按 `court_id` 升序加锁 → 与任何「单场预约」以及「另一活动创建」都不会形成循环等待（死锁）。
- 活动创建任何一块场冲突则**整体回滚**，绝不留下「部分锁场」的活动。
