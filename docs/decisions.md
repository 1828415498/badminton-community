# 技术与架构决策记录

> 每当项目出现重要设计选择，记录“问题、候选方案、最终决定、原因、影响”。

## ADR-0001：V1 只管理一个羽毛球馆

### 决定
V1 只考虑一个羽毛球馆，但数据库模型保留合理的 Venue → Court 关系。

### 原因
控制项目范围，避免过早引入多场馆业务。

## ADR-0002：一个活动可以对应多个球场

### 决定
Activity 通过 Reservation 与一个或多个 Court 建立关联。

### 原因
一次约球可能需要同时使用多个球场。

## ADR-0003：活动与场地预约分离建模

### 决定
Activity 与 Reservation 作为独立业务对象。

### 原因
两者生命周期不同：活动需要审核，预约负责资源占用；活动驳回/取消需要释放预约。

## ADR-0004：场地预约窗口为未来 7 个自然日

### 决定
用户可预约未来 7 个自然日内的场地；允许预约当天，但目标时段的开始时间必须晚于当前时刻（不得预约已经开始或已过去的时段）。

### 原因
相比“每天 12 点仅开放明天”，更符合活动提前规划的需求；同时允许当天预约（须晚于当前时刻），避免“今天临时想打球却约不了”的产品缺陷。

## ADR-0005：Reservation 作为统一场地占用账本（含归属不变量）

### 决定
个人预约与活动占场都写入 `reservation` 表，一条记录 = 球场 × 时段 × 归属。
`user_id` 与 `activity_id` **至多一者非空**：

- 个人预约：`user_id` 有值、`activity_id` 为空
- 活动占场：`activity_id` 有值、`user_id` 为空

不设额外的 `type` 字段，归属列本身就是判别依据。

### 原因
场地冲突检查必须只有一个数据源，否则个人预约与活动占场会互相看不见、导致重复占用。
若活动占场行也填 `user_id`，则“同一用户最多 2 个重叠有效个人预约”会被击穿（一个占 4 块场的活动会让创建者瞬间拥有 4 条重叠预约），且“我的预约”会混入活动占用的场。

### 影响
- 查询“我的预约”必须过滤 `activity_id IS NULL`
- 活动驳回/取消需在同一事务中批量释放其全部 reservation 行
- 活动关联的球场通过 reservation 行查询得到，Activity 表不存球场字段

## ADR-0006：数据库约束与 Service 层的职责边界

### 决定
数据库只兜底**等值唯一**（登录名、同馆球场名、一人一活动一条报名、一人一帖一赞）与外键、NOT NULL、默认值。
以下规则一律由 Service 层实现：时段重叠冲突、同一用户重叠时段预约上限、预约时间窗口、取消窗口、活动状态机与跨表级联、满员并发控制。

### 原因
MySQL 没有 PostgreSQL 的排除约束（exclusion constraint），无法用唯一索引表达“时间区间相交则互斥”；跨行跨时段的统计与状态级联同样无法用约束表达。

### 影响
- 场地冲突检查与报名必须走事务 + 行锁，不能依赖数据库报错
- 相关校验必须在 Service 层显式实现，写用例覆盖
- 后续若出现区间冲突需求（如营业时间排班），同样放 Service 层

## ADR-0007：认证方式采用 JWT（无状态认证）

### 状态

Accepted

### Context

- `api.md` §1.2 将认证机制标记为「待 ADR 决策」，接口设计刻意未绑定 Session 或 JWT。
- 项目是单体 Spring Boot MVP，无服务端会话管理需求，也没有被文档明确要求引入 Token 黑名单、刷新令牌等复杂机制。
- 需要明确一条边界：**身份认证（"你是谁"）与角色授权（"你能做什么"）是两个不同问题**，前者由认证层完成，后者必须由 Service / 权限层完成。

### Decision

- 登录成功由服务端签发 JWT（载荷含用户标识与角色信息），客户端在后续请求中携带。
- 服务端通过统一的认证拦截/过滤器解析 JWT，建立「当前用户」上下文；解析失败或过期 → 401（对应 `api.md` 错误码 `UNAUTHORIZED`）。
- 认证层只回答「你是谁」；普通用户 / 管理员等角色与资源归属判断一律在 Service / 权限层执行，不放在 Token 解析或 Controller 中。
- 退出登录 = 客户端丢弃 Token（MVP 无服务端黑名单），与 `api.md` §2.5 描述一致。
- MVP 不引入复杂 Token 黑名单 / 双 Token + Refresh 机制。

### Alternatives

- **Session + Cookie**：需要服务端会话存储、Cookie 管理，多端与无状态扩展性差；MVP 无此收益。
- **Spring Security + OAuth2/JWT 全栈体系**：引入完整安全框架与授权码流程，对单体 MVP 过重；可等后续有明确安全合规需求再引入。
- **双 Token（access + refresh）**：MVP 无长时间会话需求，不做。

### Consequences

- 优点：无状态、易水平扩展、前后端分离天然适配。
- 缺点：Token 有效期内无法被服务端主动吊销（例如"踢人下线"、改密后旧 Token 立即失效均不支持）——MVP 接受此限制；若未来需要强注销能力，再补黑名单或迁移 Session。
- 对现有文档无冲突：`api.md` §1.2 / §2.2 / §2.5 的「待确认」表述即由本 ADR 落定；401/403 语义与 `api.md` §10 一致。

### Implementation Notes

- 登录成功签发 Token，明文信息最小化（用户 id、role 即可）。
- 全局拦截器负责解析并放行匿名接口（注册/登录/公开列表）；解析成功后将当前用户放入上下文。
- 密钥与有效期走配置；JWT 过期/签名错误统一映射为 401。
- 角色校验与资源归属校验写在 Service 层（如审核人必须是管理员、活动取消者必须是创建者），Controller 不承担授权逻辑。

## ADR-0008：持久层采用原生 MyBatis

### 状态

Accepted

### Context

- `database.md` §7 与 `business-flows.md` 明确：时段冲突、并发行锁、批量级联释放等核心规则依赖**显式 SQL**（如区间相交查询、`SELECT ... FOR UPDATE` 行锁、条件批量更新）。
- 项目不使用软删除、不使用乐观锁字段；框架自动生成的 SQL 行为（如自动填充、逻辑删除约定）反而可能与现有设计冲突或掩盖 SQL。
- 需要保证每条复杂查询都有开发者可审查、可控制的明确 SQL。

### Decision

- 持久层使用**原生 MyBatis**，开发方式为 Mapper 接口 + XML/注解 SQL。
- 简单查询可用注解 SQL；复杂/动态/并发相关 SQL（冲突检查、行锁、批量释放、报名计数等）写入 XML，保证显式可见。
- **不使用 MyBatis-Plus 的自动 CRUD / 通用 Service 作为核心开发方式**；不引入其逻辑删除等隐含约定。

### Alternatives

- **MyBatis-Plus**：通用 CRUD 与条件构造器能减少样板代码，但 SQL 隐式化、自带逻辑删除等约定与「全表不软删、SQL 必须可控」的设计取向冲突，MVP 收益不显著。
- **Spring Data JPA / Hibernate**：对象关系映射对复杂区间查询、行锁、批量更新的表达与调优不如显式 SQL 直观，容易产生黑盒 SQL。
- **JOOQ / QueryDSL**：类型安全 SQL 是合理方案，但引入额外编译期 DSL，对当前团队与文档体系收益不明确，暂不采用。

### Consequences

- 优点：SQL 完全可控、可审查，与 `database.md` / `business-flows.md` 中的事务与并发要求一一对应；无框架隐含行为。
- 缺点：样板代码与手写 SQL 工作量上升，对 SQL 编写规范要求更高。
- 与现有文档无冲突：9 张表结构、约束与索引均可在原生 MyBatis 下直接落地。

### Implementation Notes

- Mapper 接口按模块划分；XML 存放于与接口同包的 resources 目录。
- 分页参数统一约定（复用 `api.md` §1.3 的 page/page_size），不引入第三方分页插件依赖（可选评估）。
- 事务边界放在 Service 层统一控制；行锁 SQL、区间冲突查询必须显式编写并命中 `database.md` §5 的索引。
- SQL 字段命名与表字段（snake_case）保持一致，不使用 map-underscore 之外的隐式转换约定。

## ADR-0009：统一响应采用 Result&lt;T&gt;

### 状态

Accepted

### Context

- `api.md` §9 给出了候选统一响应结构 `{code, message, data}`，并标注「待最终技术决策确认」。
- Controller 层需要统一的成功/失败表达方式，避免每个接口手工拼接返回对象，也避免前端被迫同时解析 HTTP 状态码与响应体两套语义。

### Decision

- 所有正常业务接口统一返回 `Result<T>`：`code=0` 表示成功；业务失败使用项目定义的标准业务错误码（以 `api.md` §10 错误码总表为准）并附可展示的 `message`。
- HTTP 状态码策略**继续遵循 `api.md` §10**：200 承载全部业务结果（成功与业务失败都看 code）；400/401/403/404/500 仅表达参数格式 / 认证 / 授权 / 路径不存在 / 未预期异常。
- Controller 不手工拼装返回对象：成功与失败由统一封装与全局异常处理完成。

### Alternatives

- **裸 DTO 直接返回 + HTTP 状态码表达一切**：错误语义分散在 HTTP 层，客户端需维护双通道解析，`api.md` §10 已分析 MVP 不采用 409 等语义化映射的原因。
- **仅 HTTP 状态码（如 409）表达业务冲突**：与 `api.md` §10「业务规则失败统一 200 + code」的决定冲突，不采用。
- **每接口自定义响应对象**：样板代码膨胀且契约不统一，不采用。

### Consequences

- 优点：前后端契约单一；错误码集中管理；新增接口无需重复设计返回结构。
- 列表数据沿用 `api.md` §1.3 的统一结构 `{list, total, page, page_size}`，不与 Result 冲突（嵌套于 data）。
- 需要约束团队：业务失败必须走标准错误码，不得在 Controller 内联返回临时错误对象。
- 与现有文档无冲突：本 ADR 将 `api.md` §9/§10 的「待最终技术决策确认」正式落定。

### Implementation Notes

- 定义统一 `Result<T>`、业务错误码枚举与全局异常处理器。
- Service 抛出的业务异常与框架校验异常（如参数错误）统一转换为 Result 规范结构，参数类归 `PARAM_INVALID` / HTTP 400。
- 认证与授权异常保持 HTTP 401/403（见 ADR-0007），但响应体仍可复用 Result 结构。
