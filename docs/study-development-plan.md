# 大三后端实习：学习与项目推进总计划

> 目标：在大三阶段，以“羽毛球活动与场地预约平台”为主项目，具备中厂 Java 后端实习面试所需的项目表达、核心技术和动手能力。
>
> 时间预算：工作日每周 15–20 小时；上午算法 2–3 小时，下午约 2 小时做项目，晚上用于复盘或技术补充；周末以休息为主。

---

## 0. 先统一策略：不是二选一

当前不应该在“先把整个项目读完”和“立刻加 Redis/MQ”之间二选一。

采用的主线是：

```text
先掌握一个高价值业务链路
  ↓
亲手修复/补测试，证明自己能改
  ↓
在真实痛点上补一项技术能力
  ↓
再进入下一条业务链路
```

因此前两周的重点是**项目主导权恢复 + 修复预约并发超卖**。这是理解项目和提升简历价值的交集。只有当一项现有能力已经能被解释、修改、测试后，才继续引入 Redis、MQ、Docker 等新能力。

结合目标 Java 后端实习岗位要求，**MQ 是本计划的主项目必做能力，ES 是按目标岗位决定的扩展能力**。“必做”指完成一个真实业务场景并验证可靠性，不代表现在跳过预约并发问题直接接入中间件。岗位写有某技术，也不等于必须把它塞进预约核心链路；简历只写自己实现、验证并能解释的能力。

### 一项能力何时算“属于自己”

以下 5 项全部满足，才算掌握，也才可以写成简历亮点：

1. 能用两分钟说明它的业务目标。
2. 能画出 Controller → Service → Mapper → SQL/表 的请求路径。
3. 知道关键字段、状态值、不变量和异常分支。
4. 能独立完成一个小改动或修复一个小问题。
5. 能运行测试，并说明测试保护的风险。

## 1. 每日固定节奏

### 上午：算法（2–3 小时）

每天 2–4 题，但要带复习。

| 时间 | 任务 | 目的 |
|---|---|---|
| 20 分钟 | 复习 2 道旧题：不看答案复述思路并手写核心逻辑 | 防止“刷过即忘”，训练面试口述 |
| 90–120 分钟 | 新题 2–3 道，按主题连续训练 | 建立模板：双指针、滑窗、二分、链表、栈队列、树、回溯、动态规划 |
| 20 分钟 | 错题记录：题型、错误点、复杂度、下次复习日 | 形成可回顾的错题库 |

复习间隔：首次完成后第 1、3、7、14 天复习。若无法独立写出，重新进入“新题”队列。

### 下午：项目（约 2 小时）

| 时间 | 任务 | 目的 |
|---|---|---|
| 25 分钟 | 阅读当天指定链路，画调用图 | 重新获得项目全局与局部认知 |
| 35 分钟 | 用自己的话解释设计；记录不懂的问题 | 训练面试表达，暴露真实盲区 |
| 45 分钟 | 实现一个小改动、测试或排障动作 | 从“看懂”变成“会改” |
| 15 分钟 | 更新项目知识卡片与日报 | 沉淀可用于复盘和简历的证据 |

### 晚上：后端八股 + 当日复盘（45–75 分钟）

晚上固定加入八股，但不按网上题库随机背诵。题目必须服务于当天正在读或正在改的项目模块；这样每一个答案都有项目案例，面试时不会变成空话。

| 时间 | 任务 | 目的 |
|---|---|---|
| 25–35 分钟 | 学 2–3 个当日主题的高频八股题：先自己回答，再查资料补全 | 形成结构化回答，而非死记结论 |
| 10–15 分钟 | 将其中 1 题关联到本项目，写出“项目中我怎么做/会怎么做” | 把理论转化成项目表达 |
| 10–15 分钟 | 回顾当天项目任务：不看代码复述一次链路与一个风险点 | 巩固主动回忆，及时暴露盲区 |

每周五晚上做一次 30 分钟小测：随机抽本周 10 题，要求脱稿回答；答不出的题加入下周复习队列。

#### 八股主题与项目阶段绑定

| 项目阶段 | 晚上八股主题 |
|---|---|

| 第 2 周：预约并发 | RR 与 RC、快照读/当前读、MVCC、行锁/间隙锁、死锁、乐观锁与悲观锁、幂等性 |

| 第 5 周：Redis | 常用数据结构、过期策略、淘汰策略、缓存穿透/击穿/雪崩、缓存一致性、持久化 |

## 3. 八周每日执行计划

### 开始顺序：先业务设计和数据库设计，但只读“核心路径”

你**需要从业务设计和数据库设计开始**，但不是花一两周把所有文档逐字读完，也不是脱离代码空看 ER 图。

正确顺序是：

```text
核心业务规则（用户要完成什么）
  ↓
核心数据模型（用哪些表和字段保障规则）
  ↓
对应的 Controller / Service / Mapper / SQL
  ↓
测试、并发风险和亲手修改
```

以“创建个人预约”为例：先读 7 天窗口、整点、冲突、个人上限、取消窗口这些业务规则；再看 `reservation`、`court`、`user` 的表结构与索引；最后进入 `ReservationService` 和 SQL。这样看代码时每一个判断都有业务来源，每一个字段都有存在理由。

因此，本计划第 1 周的周一、周二就是业务设计和数据库设计同步；周三开始才进入鉴权和具体代码链路。按此路线推进即可。

### 第 1 周：项目地图与预约链路

目标：能说清系统做什么、模块如何协作；能独立解释一次个人预约的完整流程。

| 天 | 当天任务 | 目的与验收 |
|---|---|---|
| 周一 | 启动前后端；浏览全部页面；阅读 `README.md`、`docs/requirements.md`、路由表和 API 模块 | 画出功能地图；能在 3 分钟介绍项目范围 |
| 周二 | 阅读 `sql/schema.sql`、`docs/database.md`；画 9 张核心表关系 | 掌握数据模型；能解释为何 `reservation` 同时记录个人预约与活动占场 |
| 周三 | 跟读登录链路：`AuthController`、`UserService`、`JwtUtil`、`AuthInterceptor`、前端 user store | 能解释注册、BCrypt、JWT 签发和鉴权流程 |
| 周四 | 跟读个人预约：`ReservationController` → `ReservationService.create` → Mapper SQL | 写出预约的校验、锁、查重、插入四个阶段 |
| 周五 | 阅读预约相关单元/集成/并发测试；自己修改一个预约测试断言或增加边界用例 | 能说明每类测试保护什么；产出预约模块知识卡片 |

### 第 2 周：并发超卖修复

目标：亲手解决当前最高优先级缺陷，让并发回归测试转绿。

| 天 | 当天任务 | 目的与验收 |
|---|---|---|
| 周一 | 复现 `ReservationConcurrencyTest`；阅读 `docs/known-issues.md`；画出 4 个线程的事务时间线 | 能解释为什么“已经锁了 court 行”仍可能 4 人都成功 |
| 周二 | 学习并做小实验：MySQL RR 下快照读、当前读、`SELECT ... FOR UPDATE` | 不背概念；能用本项目 SQL 说明快照何时建立 |
| 周三 | 比较修复方案：锁定查询、调整事务边界、隔离级别、独立锁行；写出选择理由和风险 | 作出设计决策，而非直接接受代码答案 |
| 周四 | 实现修复；保持统一锁顺序；运行预约相关测试 | 并发测试由红转绿，原有预约规则不回归 |
| 周五 | 代码复盘：解释最终 SQL/事务边界；补“并发超卖修复说明”和面试问答 | 形成项目最重要的可讲亮点 |

### 第 3 周：活动、报名与状态机

目标：掌握第二条核心链路，并验证名额不会超卖。

| 天 | 当天任务 | 目的与验收 |
|---|---|---|
| 周一 | 跟读活动创建和活动占场：`ActivityService`、活动/预约 Mapper | 能解释为何创建待审核活动也要先占用场地 |
| 周二 | 跟读审核、驳回、取消、结束任务；画 activity 状态机 | 能列出每个状态允许的操作和关联数据变化 |
| 周三 | 跟读 `RegistrationService`；分析重复报名、取消后重报和名额统计 | 能解释唯一索引与业务幂等的区别 |
| 周四 | 编写“多人抢最后一个名额”的并发集成测试；根据结果确认/修复问题 | 用测试验证报名不会超卖，而非只相信行锁注释 |
| 周五 | 模拟面试：活动状态机、活动取消的级联、预约与活动的冲突 | 能连续回答至少 10 分钟并完成知识卡片 |

### 第 4 周：代码质量与接口治理

目标：让项目从“能运行”变成“可维护、可排障”。

| 天 | 当天任务 | 目的与验收 |
|---|---|---|
| 周一 | Review 全局异常、错误码、参数校验和分页；列出不一致处 | 建立统一 API 契约意识 |
| 周二 | 为关键写接口设计幂等方案：至少覆盖预约创建或报名 | 能说明重复点击、网络重试如何处理 |
| 周三 | 增加请求 ID 与关键业务日志（预约、报名、审核） | 出问题时能关联一次请求和业务结果 |
| 周四 | 增加管理员操作审计表/日志，记录审核和强制取消 | 补充可追溯性，形成真实管理端能力 |
| 周五 | 整理 API 文档与 README 现状差异；修正明显失真的项目说明 | 项目说明与真实能力一致，可供面试官查看 |

### 第 5 周：Redis 缓存与一致性

目标：基于热点读场景引入 Redis，而不是为了技术栈而引入。

| 天 | 当天任务 | 目的与验收 |
|---|---|---|
| 周一 | 通过日志或接口分析确定缓存对象：场馆/球场、已发布活动列表、首页聚合数据 | 每个缓存都有读多写少的业务理由 |
| 周二 | 用 Docker 启动 Redis；完成 Spring Boot Redis 基础连接和序列化实验 | 掌握连接、序列化、TTL，不直接塞进业务 |
| 周三 | 实现 Cache Aside：查询回源与写入缓存；定义 Key 和 TTL | Redis 未命中时可正确回源 MySQL |
| 周四 | 在活动审核/取消、球场启停时实施缓存失效；补缓存一致性测试 | 能解释“为什么删缓存而非直接更新缓存” |
| 周五 | 补空值缓存、缓存穿透与热点 Key 的处理方案；做 Redis 面试复盘 | 能说清缓存三大问题在本项目的具体处理 |

### 第 6 周：Docker 化与可部署性

目标：任何人拿到仓库都能一键启动完整环境。

| 天 | 当天任务 | 目的与验收 |
|---|---|---|
| 周一 | 梳理配置项：数据库、Redis、JWT、上传目录；将敏感配置改为环境变量 | 消除代码库中的硬编码生产配置 |
| 周二 | 编写后端 Dockerfile，构建并启动容器 | 容器内可连接外部依赖并提供 API |
| 周三 | 编写前端 Dockerfile 或静态构建 + Nginx 配置 | 前端可正确代理 `/api` |
| 周四 | 编写 Docker Compose：frontend、backend、MySQL、Redis | 一条命令启动完整开发演示环境 |
| 周五 | 从零环境验证部署，补健康检查与部署文档 | 可复现、可演示、可交付 |

### 第 7 周：候补队列与 MQ（主项目必做）

目标：通过真实业务需求学习异步化、消息可靠性和最终一致性；至少完成一个可演示、可追问的 MQ 场景。预约与报名的名额/场地判定仍由数据库事务同步完成，不交给消息消费者决定。

| 天 | 当天任务 | 目的与验收 |
|---|---|---|
| 周一 | 设计“报名满员后候补、有人取消后递补”规则和表结构/状态机 | 明确候补顺序、取消、重复操作和边界 |
| 周二 | 实现候补入队与取消；补事务和并发测试 | 候补顺序正确且不超员 |
| 周三 | 将 RabbitMQ 加入 Docker Compose；学习交换机、队列、确认、重复投递，并用最小 Demo 验证 | 能从零启动消息队列并解释投递语义，不急于接入主链路 |
| 周四 | 将“递补成功通知”改为异步消息；实现消费者幂等 | 消息重复时不会重复通知或重复修改业务状态；能说明数据库提交与发消息之间的失败窗口 |
| 周五 | 故障演练：消费者失败、消息重投、服务重启；记录最终一致性边界 | 能展示失败重试和重复消费的验证结果，回答消息丢失、重复、最终一致性追问 |

若候补业务设计或实现超出本周时间预算，MQ 学习不因此无限延期：改用已有的“活动审核通过/驳回后发送通知”作为最小真实场景。两种场景只选一种做扎实；先明确通知记录的持久化、发送失败的处理方式，再决定是否需要 Outbox，不宣称没有验证过的“消息绝不丢失”。

### 第 8 周：项目收口、压测与面试表达

目标：将成果转化成可验证的简历项目和面试表现。

| 天 | 当天任务 | 目的与验收 |
|---|---|---|
| 周一 | 对预约、报名、活动列表做压测；记录机器、并发、指标和瓶颈 | 只使用真实测得的数据，不编造 QPS |
| 周二 | 根据压测优化 SQL/索引或缓存；用前后数据对比验证 | 能解释一次具体性能优化 |
| 周三 | 更新项目架构图、ER 图、部署图、关键时序图 | 让项目结构可快速展示 |
| 周四 | 写简历项目描述；每条描述对应真实代码、测试或数据证据 | 形成可信、可追问的简历内容 |
| 周五 | 进行一次完整项目模拟面试：自我介绍 + 深挖并发/Redis/MQ/Docker | 找出无法回答的问题，进入下一轮学习清单；核对 MQ 简历描述与代码、故障测试一致 |

## 4. 技术引入顺序与边界

| 技术 | 何时引入 | 在本项目中的正确职责 | 暂不做的事 |
|---|---|---|---|
| MySQL 事务/行锁 | 现在 | 预约、报名的最终正确性与并发互斥 | 不用 Redis 锁替代数据库约束 |
| Redis | 第 5 周 | 热点读缓存、缓存一致性、短期数据 | 不缓存所有查询；不把 Redis 当主数据源 |
| Docker | 第 6 周 | 环境一致、可复现部署 | 不急于 Kubernetes/复杂 CI/CD |
| MQ | 第 7 周，主项目必做 | 候补递补成功通知；若候补延期则用活动审核结果通知。至少完成投递、消费、重复消费幂等和失败重试验证 | 不把预约、名额扣减等核心正确性判断改为异步；不把“接入了 MQ”写成“掌握高可靠消息” |
| 分布式锁 | 后续多实例时评估 | 跨实例协调；且必须保留数据库兜底 | 不用它修当前单体预约超卖 |
| ES | 第 8 周之后按目标岗位决定 | 若多个强意向岗位明确要求，扩展社区帖子全文搜索，验证建索引、数据同步和查询结果；否则学习核心概念并做小实验 | 不因技术栈焦虑提前接入；不把只会调用查询接口写成项目亮点 |
| 微服务 | 实习前不作为主线 | 只在明确业务边界出现后评估 | 不为简历拆微服务 |

### 岗位要求如何影响 ES 决策

第 6–8 周整理至少 10 个自己真正愿意投递的 Java 后端实习岗位，记录城市、毕业届别、技术要求以及“必需/优先/工作中学习”的措辞。若 ES 在多个强意向岗位被明确要求，再排一个独立扩展阶段；若只是少数岗位提及，不推迟主项目收口和投递。招聘页摘要不完整时，不能把“摘要未写 ES”统计为“岗位不要求 ES”。MQ 即使出现在岗位技术栈中，也要区分“了解概念”与“能处理可靠投递、重复消费”的深度要求。

## 5. 每周产出与检查点

每周五完成以下四项：

1. 一个可运行的提交或一组通过的测试。
2. 一张或多张项目知识卡片。
3. 五个本周技术问题的口头回答录音/文字稿。
4. 一份下周计划：未完成事项、原因和调整动作。

如果某周任务未完成，不跳过直接加新技术。优先收口当前模块，保证每一个写进简历的能力都能经得起追问。

## 6. 简历可用的最终能力目标

八周完成后，只有在对应功能真实实现、测试或压测验证完成的前提下，才使用下列方向描述项目：

- 统一预约账本建模个人预约与活动占场，并基于事务、锁和并发测试解决时段超卖。
- 设计活动审核、报名、候补与取消的状态流转，保证关键关联数据一致。
- 使用 Redis 实现热点数据缓存，并处理缓存失效、穿透和一致性问题。
- 使用 MQ 解耦候补递补/通知等异步副作用，并实现幂等消费。
- 使用 Docker Compose 编排前后端、MySQL、Redis 和消息队列，实现一键部署。

不要写未经实测的“高并发”“百万级”“分布式锁防超卖”等表述。
