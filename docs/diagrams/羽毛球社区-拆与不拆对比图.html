第四节 · 引进虚实体

同一个需求，两种建表方式

场景：一场活动要占 3 块球场。左边是"照多对多联系直录"，右边是把活动提升为虚实体（主从表）。

✗ 不拆 —— 活动占场当普通联系表，一行一块场

活动本身没有归属的表，属性只能跟着每一行重复。

activity_court一张宽表

  • 改一次开始时间 → 要改 3 行；漏改一行，数据就自相矛盾
  • 人数上限、审核状态同理 —— 一处改动要同步 N 行
  • 「活动」这个概念在库里没有主键，查一场活动只能按标题模糊匹配

✓ 拆 —— 活动当头表，占场降为明细

活动自己成为一张表（虚实体），明细只记录"占了哪几块场"。

一次创建 = 1 条 activity + N 条 reservation，包在同一个事务里

这一页怎么讲（口播）

这里是我整个设计的转折点。一个活动经常要占多块场。如果我把"活动占场"也照多对多联系表来直录， 一次占三块场就要写三行 —— 你看活动标题、开始时间、人数上限、审核状态，这四列重复了三遍。 改一次开始时间要改三行，漏一行数据就自相矛盾了。

所以我把活动提升成一个虚实体。活动自己成为一张表，只存一份；"占哪几块场"降为它的明细。 一次创建就是一条活动加 N 条占用，包在一个事务里提交。
