种子数据里的活动日期是固定的，一旦当天日期越过它们，首页就会出现「今天没有球局」、时间表全灰、没有可报名的活动。答辩当天早上跑一次，数据就是"当天"的：

脚本用 CURDATE() 相对生成，任何一天执行都合适；可重复执行。

第 1 幕 · 开场 PPT 第 2 页 · 目标定义 约 30 秒

定调：这是一个解决真实问题的系统，不是功能堆砌。

操作：打开首页，指顶部那一行「今天还有 N 场球 · 还缺 M 人」。

讲解词

我做的是一个羽毛球社区管理系统。要解决的问题很具体：一个球友打开手机，只想确认一件事——今晚能不能打上球。所以系统围绕两条线建：找场地（预约）和找人（球局报名）。首页不放大数字统计，第一眼就告诉你今天有几场、还差不差人。

第 2 幕 · ER 图 PPT 第一节 约 2 分钟

交代实体与联系，重点标出四个 M:N。

打开：羽毛球社区-ER图.html

讲解词

9 张表对应 6 个实体、9 个联系。这里我要特别指出四个多对多联系（红色的菱形）：报名（用户×活动）、点赞（用户×帖子）、预约（用户×场地）、占场（活动×场地）。

在 ER 图里它们是菱形，落库时前两个各变成一张联系表；后两个我合并进了同一张占用台账——这是第 6、7 幕要讲的。

指给老师看：四个红色 M:N 菱形，以及实体框内带下划线的主键。

第 3 幕 · 数据表设计 PPT 第二节 约 2 分钟

讲清 9 张表的划分依据，以及"不设导出项"。

打开：羽毛球社区-关系模型明细.html

表的类型表ER 图里画什么
实体表user / venue / court / activity / post / comment矩形
M:N 落成的联系表registration / post_like菱形
合并表reservation两个菱形合成一张
讲解词

判断标准是：有没有独立的代理主键、承载的是"东西"还是"关系"。

还有一条我特意遵守了：表里不出现任何"能算出来"的字段。点赞数、报名人数我一个都没建字段——全部用视图实时 COUNT。因为一旦落成字段，就必然出现"点赞表加了行、计数字段忘了更新"的不一致。

指给老师看：post 卡片下方那行「本表没有 status，也没有 like_count」。

第 4 幕 · 实体表增删改查 PPT 第三节 (1) 约 3 分钟

证明"增"用了控件、"删"有确认框且受完整性约束。

动作操作路径讲解要点
增退出登录 → 注册页，注册一个新用户不是全文本框裸填：有长度校验、重复校验
改个人资料 → 编辑资料：改昵称 + 传头像头像是文件上传，不是填 URL

讲解词

删除我统一用确认框，而且都受完整性约束。删帖子会连带清掉它的评论和点赞——这是数据库的外键 ON DELETE CASCADE 做的，不是前端删两次。

第 5 幕 · 联系表操作 + 视图 PPT 第三节 (2) 约 3 分钟

演示 M:N 落成的表怎么增删，以及"视图的完整查询"。

（a）报名 · M:N 落成的表

  • 操作：首页 → 找到「今晚双打，还差 3 人」→ 点「加入球局」
讲解词

加入球局写的是 registration 表——用户与活动的多对多联系。一条 uk_registration_user_activity 唯一约束保证一个人报不了两次。

（b）预约 · 写进占用台账

  • 操作：场地 → 在时间表上点两个空格定起止 → 确认预约
讲解词

点两个空格确定起止时段，写进 reservation。同一块场、同一时段只能有一条有效占用——靠 SELECT ... FOR UPDATE 加锁判冲突，不是靠唯一约束，因为"已取消"的行还留在表里。

（c）查 · 视图（PPT 明确点名的一项）

打开 MySQL 命令行执行：

SELECT * FROM v_reservation_detail LIMIT 10;
讲解词

占用表里存的全是编号——球场 id、用户 id、活动 id，直接查读不懂。所以我定义了视图 v_reservation_detail，把场馆名、球场名、占用方、来源、时长、状态文本一次 JOIN 出来。

我系统里的「打印凭证」就是查这条视图出来的——视图不是躺在 SQL 文件里看的，它真的在给系统供数。

加分句：另外两条视图 v_post_with_stats（帖子+评论数+点赞数）和 v_activity_signup_stat（报名进度），正是"点赞数、报名人数不该建字段"的正面教材。

第 6 幕 · 引进虚实体 最重要的考点 PPT 第四节 约 4 分钟

讲清"为什么把活动拆成头 + 明细"，并在现场真的录一次主从表。

先讲原理：

讲解词

一个活动常常要占多块场。如果我把"活动占场"也做成一张普通的联系表，一次占 3 块场就要写 3 行——活动的时间、人数上限、审核状态就要重复 3 遍。这是重复录入和数据冗余：改一次开始时间，要改 3 行。

所以我把「活动」提升成一个虚实体（头表），把"占哪几块场"降为它的明细。一次创建 = 1 条活动 + N 条占用行，包在同一个事务里。

现场操作：

  1. 球局 → 发起球局
  2. 填标题、描述
  3. 选开始 / 结束时间 —— 日期时间控件，自动对齐整点
  4. 填人数上限 —— 数字控件
  5. 选择球场：勾选任意多块 ← 这就是"明细行数不固定"
  6. 提交 → 弹确认框 → 确认

验证落库（可切到命令行，当场看）：

SELECT id, title, status FROM activity ORDER BY id DESC LIMIT 1;
SELECT court_id, start_time, end_time
  FROM reservation WHERE activity_id = <刚创建的活动 id>;

会看到：1 条 activity + N 条 reservation（activity_id 有值、user_id 为 NULL）。

这一句最值钱："这不是我事后补的，是我建表时就这么设计的——所以我至今不需要写任何'同步'代码。"
第 7 幕 · 管理台：审核与球场维护 补上状态流转 PPT 第三节 (1) 约 3 分钟

把"发起活动"接下去 —— 审核通过后才开放报名；顺带补完实体表的增 / 改。

入口：右上角头像 → 「管理台」（只有管理员看得到这一项）

（a）审核球局 —— 刚才发起的那场正在这里等着：

  1. 在「待审核球局」里找到刚提交的那场（或预留的「今晚临时加一场」）
  2. 点「驳回」→ 弹出输入框，必须填原因（原因会存进 reject_reason 并展示给发起人）→ 场地释放
  3. 换一场点「通过」→ 确认框 → 活动转为「报名中」，报名开放
  4. 回到球局详情，报名按钮已经能点了
讲解词

审核是这套设计里唯一的状态流转。驳回必须给原因 —— 不是只改一个状态码，而是让发起人知道"哪里不合规"。驳回和取消都会自动释放场地。

（b）球场维护 —— 实体表的增 / 改 / 停用：

动作操作讲解要点
增「新增球场」→ 输入名称同场馆重名会被唯一索引 uk_court_venue_name 挡下
改「改名」→ 输入新名同样受唯一约束
停用「停用」该场地有未来有效预约时，后端会拒绝
启用「启用」恢复可预约
一个很好的演示技巧：直接停用 1 号场会被拒绝（它今天有活动占场）—— 这一下就把"完整性约束"演活了。
想演示"停用成功"，就现场新增一块 7 号场再停用它：新场地没有预约，一次通过。这样"被拒绝"和"成功"两种结果都演到了。
老师可能追问权限：前端隐藏菜单只是体验，真正的授权在后端。每个 /api/admin/* 在 Service 层调 requireAdmin()，普通用户直接 403 —— 已实测。这就是 ADR 里"认证与授权分离"的落地。
第 8 幕 · 改进后的关系模型 PPT 第四节 约 2 分钟

交代拆分的最终形态，并解释那个"二选一"约束。

打开：羽毛球社区-表关系图.html —— 这张就是"改进后的关系模型"（表卡片 + 外键连线 + 基数，字段与 schema.sql 逐列一致）

讲解词

改进后的结果是：活动是头，占用是明细。但明细我没有单独开一张 activity_court 表，而是和"个人预约"合并进了同一张 reservation。

理由是——"同一球场同一时段只能有一条有效占用"是一个全局不变量。如果个人预约和活动占场分两张表，判冲突就要 UNION 两张表再分别加锁，竞态窗口翻倍。合并后，这个不变量只需要在一个地方守。

代价是这张表承担了两种语义。所以我用一条 CHECK 约束钉死：

CONSTRAINT chk_reservation_owner
  CHECK ((user_id IS NULL) <> (activity_id IS NULL))

强制二选一：要么是个人预约（user_id 有值），要么是活动占场（activity_id 有值），不可能两者都有或都没有。

另外我把自己踩到的一个并发缺陷整理成了一份分析文档：4 个用户同时约同一时段，早期版本会全部成功。追下来是 InnoDB 在 REPEATABLE READ 下，SELECT ... FOR UPDATE 是当前读，但后面的 COUNT(*) 走的还是事务最早建立的旧快照——锁是对的，读到的是旧数据。修法是让冲突判断也走当前读。

3必答问题

老师大概率会问这几个。答案背下来，比多做十页 PPT 有用。

Q1reservation 为什么把个人预约和活动占场塞进同一张表？

因为"同一球场同一时段只能有一条有效占用"是全局不变量。分两张表就要 UNION 后分别加锁，竞态窗口翻倍；合并后只需守一处。代价是双语义，用 chk_reservation_owner 强制 user_id / activity_id 二选一。

Q2registration 已经有 id 主键了，为什么还要 (user_id, activity_id) 唯一约束？

id 是代理键，给程序引用用的；(user_id, activity_id) 才是业务规则（一个人在同一活动只能报一次）。两者职责不同，不能互相替代。

Q3post_like 为什么干脆不要 id 主键？

因为这张表的"身份"就是"谁赞了哪帖"，复合主键 (post_id, user_id) 本身就是那条业务规则，再加代理键是多余的。

Q4为什么不给 post 加 like_count 字段？

点赞数是能算出来的量，属于"导出项"。一旦落成字段，就会出现"点赞表加了行、计数字段忘了更新"的不一致。我把它放进视图 v_post_with_stats 实时 COUNT。

Q5活动占场为什么不算个人预约？

两者的"归属"不同：个人预约的占用方是用户，活动占场的占用方是活动。是活动占场时 user_id 必须为 NULL、activity_id 有值——由 CHECK 约束强制。

Q6取消预约为什么不是物理删除？

因为要留痕，且"取消后释放时段"是靠 status=2 让冲突判断忽略它。物理删掉就查不到历史了。

Q7一个人能不能重复报同一个活动？

不能。数据库层靠 uk_registration_user_activity 唯一约束兜底，应用层在报名前先查一次并给出友好提示。

Q8并发情况下怎么保证不超卖？

报名和预约都走事务 + SELECT ... FOR UPDATE。这里有份踩坑文档（known-issues.md）——我第一版就是栽在 RR 隔离级别的一致性读快照上。
