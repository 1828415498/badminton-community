羽毛球社区管理系统 · ER 图（实体-联系图）

矩形＝实体　·　菱形＝联系　·　连线上的 1 / N / M 为基数　·　实体框内主键加下划线　·　FK 标注引用方向

关系模式（主键加下划线，箭头为外键引用）

user (id, username, password_hash, nickname, avatar_url, role, create_time, update_time)
venue (id, name, address, create_time, update_time)
court (id, venue_id, name, status, create_time, update_time) → venue(id)
activity (id, creator_id, title, description, start_time, end_time, max_members, status, reviewer_id, review_time, reject_reason, create_time, update_time) → user(id)
post (id, user_id, title, content, create_time, update_time) → user(id)
comment (id, post_id, user_id, content, create_time) → post(id), user(id)
registration (id, user_id, activity_id, status, create_time, update_time) → user(id), activity(id)；用户+活动唯一
post_like (post_id, user_id, create_time) → post(id), user(id)；复合主键
reservation (id, court_id, user_id, activity_id, start_time, end_time, status, cancel_time, create_time, update_time) → court(id), user(id), activity(id)

四个多对多联系 → 实现时落了哪些表

联系（菱形）两端基数落成的表说明
报名user – activityM : Nregistration代理主键 + (user_id, activity_id) 唯一约束
点赞user – postM : Npost_like复合主键 (post_id, user_id)，一人一帖一赞
预约user – courtM : Nreservation两个联系合并成同一张场地占用台账，用 user_id / activity_id 二选一 区分
占场activity – courtM : N
为什么最后两个 M : N 没有各建一张表？
因为「同一球场同一时段只能有一条有效占用」是一个全局不变量，不管这次占用来自个人预约还是活动占场。 如果两类占用分在两张表里，判定冲突就要 UNION 两张表、再分别加锁，竞态窗口直接翻倍； 收进同一张 reservation 台账，不变量就只有一个地方需要守。
代价是这张表承担了两种语义 —— 所以建表时用一条 CHECK 约束把它钉死：
CONSTRAINT chk_reservation_owner CHECK ((user_id IS NULL) <> (activity_id IS NULL))
「个人预约」行的 activity_id 必空，「活动占场」行的 user_id 必空，两者不可能都有或都没有。
