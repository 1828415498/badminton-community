羽毛球社区管理系统 · 关系模型明细

9 张表逐张展开：字段 / 类型 / 可空 / 键 / 说明，以及每张表的上级（它引用谁）与下级（谁引用它）。配合 ER 总图使用。

依赖层级：谁在最上面，谁在最下面

user　（根表，不依赖任何表）
├── venue　（根表，不依赖任何表）
│　　└── court　venue_id → venue
│　　　　　　└── reservation　court_id → court
├── activity　creator_id → user、reviewer_id → user
│　　├── registration　activity_id → activity
│　　└── reservation　activity_id → activity
├── post　user_id → user
│　　├── comment　post_id → post（级联删除）
│　　└── post_like　post_id → post（级联删除）
└── reservation　user_id → user　（个人预约行；活动占场行此列为 NULL）
comment　user_id → user
post_like　user_id → user

字段类型键说明

post_idBIGINTFK NN所属帖子 → post(id)，级联删除

post_like帖子点赞「点赞」M:N 联系落成的表
字段类型键说明
post_idBIGINTPK FK NN被点赞帖子 → post(id)，级联删除
user_idBIGINTPK FK NN点赞用户 → user(id)
create_timeDATETIMENN点赞时间
上级post_id → post(id)　user_id → user(id)
下级无
约束复合主键 (post_id, user_id) —— 不需要额外的唯一约束，「一人一帖一赞」由主键本身保证；索引 idx_post_like_user；两个外键均 ON DELETE CASCADE
三种表的划分依据（答辩可以照着说）：
① 实体表（user / venue / court / activity / post / comment）—— 有自己独立的代理主键 id，承载独立业务属性，在 ER 图里画矩形。
② 联系落成的表（registration / post_like）—— 主键由两端主键组成或等价于它的唯一约束，本质是「关系」而不是「东西」，在 ER 图里画菱形。
③ 合并表（reservation）—— 特殊：把「预约」和「占场」两个 M:N 联系合并成一张表，用 user_id / activity_id 二选一来区分，靠 chk_reservation_owner 约束钉死。这是本项目最有设计感的一张表。
